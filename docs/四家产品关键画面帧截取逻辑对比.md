## 二、通义听悟：官方写明的 8 步流程

来源：阿里云开发者社区《2024 通义语音 AI 技术图景》中的「多模态分割：PPT 视觉边界检测及大模型摘要」一节，以及阿里云帮助中心《PPT抽取及摘要》。

官方原文描述的流程：

```text
1. 以固定时间间隔从视频中采集视频帧，得到视频帧序列
2. 前景物体过滤
3. 依据运动和静止事件检测结果，锚定 PPT 切换的时间戳
4. 时间戳校准
5. 相似度去重
6. OCR 识别 PPT 内容
7. 对齐视频转写的文本和 PPT 内容
8. 输入摘要大模型，得到每张 PPT 对应讲解内容的摘要
```

### 每一步在干什么

**第 1 步：固定间隔采样，不是场景检测。**
这一步和大多数人的直觉相反。通义不是"检测画面变了才取帧"，而是先等间隔抽一堆帧，后面靠运动/静止分析去判断哪些帧是 PPT 页。原因是 PPT 切换时常常有动画过渡（淡入、翻页），如果等"检测到变化"再取帧，拿到的很可能是过渡中间态。先密集采样再事后判断，才有挑稳定帧的余地。

**第 2 步：前景物体过滤。**
把画面里不属于 PPT 的东西去掉，比如走到投影前的人、飘过的鼠标指针。官方功能说明里对应这条限制："仅支持 PPT 在主要界面（投屏或周边有人物视频），不支持人物在 PPT 前走动或演讲"。也就是说，人在 PPT 前来回走这个场景，前景过滤处理不了，功能直接不可用。

**第 3 步：用运动和静止事件锚定切换点。**
这是核心。逻辑不是"画面变了"，而是"画面变完之后进入了一段静止"。PPT 一页会停留十几秒到几分钟，这个持续静止的窗口才是判定依据：静止窗口开始 = 这一页 PPT 的开始时间，静止窗口结束 = 下一页开始。这样天然过滤掉了翻页动画、鼠标移动、临时弹窗这些短时变化。

**第 4 步：时间戳校准。**
把采样帧的时间戳修正到真实的切换时刻。因为第 1 步是等间隔采样，采到的帧和真实切换点之间存在最大一个采样间隔的误差，需要回退修正。

**第 5 步：相似度去重。**
同一页 PPT 可能在多个采样点上都被判定成"静止窗口的一帧"，用相似度去掉重复，保证一页只留一张。

**第 6 步：OCR。**
识别留下来的 PPT 图片上的文字。

**第 7 步：与 ASR 文本对齐。**
把每页 PPT 的起止时间和转写文本按时间对齐，得到"这一页停留期间讲了什么"。

**第 8 步：摘要模型。**
把对齐结果喂给摘要模型，输出每页 PPT 对应的讲解摘要。

### API 返回结构

请求参数只有一个开关：

```json
"Parameters": { "PptExtractionEnabled": true }
```

结果里 `PptExtraction` 指向一个 JSON 文件，结构如下（官方示例，字段已核实）：

```json
{
  "PptExtraction": {
    "AvailableForSummary": true,
    "PdfPath": "https://.../ppt_20231031110531/....pdf",
    "KeyFrameList": [
      {
        "Id": 1,
        "Start": 1160,
        "End": 12320,
        "FileUrl": "https://.../...._001.png",
        "Summary": "介绍了达摩院的工作和岗位要求……"
      }
    ]
  }
}
```

| 字段 | 含义 |
|---|---|
| `Id` | 序号 |
| `Start` / `End` | 这一页 PPT 的开始/结束时间，毫秒，相对文件起始 |
| `FileUrl` | 抽出的 PPT 图片下载链接 |
| `Summary` | 这一页停留期间讲解内容的摘要 |
| `PdfPath` | 所有 PPT 页合成的 PDF |

这个结构本身就是一份「时间顺序纪要」的最小可用形态：一页 PPT = 一条记录，带起止时间、一张图、一段文字。

### 官方明确的边界（都要知道）

1. **只支持 PPT 为主体的视频**（投屏，或人物在 slides 旁边）。人在 PPT 前走动或演讲，不支持。
2. **实时会议场景不可用**，因为实时场景推的是音频流，没有视频画面。
3. **非视频格式的原始文件不可用**。
4. **两步执行**：先抽 PPT 图，再结合 ASR 生成摘要。如果抽到了图但对应时段 ASR 文本太短，摘要会为空（此时 `Summary`/`Start`/`End` 可能为空）。官方原话："抽取到了图片，但由于对应的ASR文本过短、过少，无法提炼出有效总结内容，此时该PPT图片对应的总结内容即为空"。
5. PPT 摘要只支持部分语种。

## 三、BibiGPT：按画面变化抽帧 + 帧数超限时按话题挑

来源：BibiGPT 官方文档《PPT 关键帧提取》《Keyframe Screenshot Analysis》，以及官方博客《视频转PPT终极指南》。

### 3.1 PPT 关键帧提取（文档明确）

官方描述：打开「PPT 提取 (Beta)」，系统**按画面变化抽出不重复的关键帧**，每张图下方汇集该时段字幕，支持 PPT 视图和 APP 视图两种浏览方式。

官方写明的边界：

> 这是从原片抽出课件画面，不是 AI 重新生成幻灯片。适合"画面本身就是教材"的课。
> 画面几乎不变的访谈视频，提取到的帧会比较少，更适合有幻灯片或板书的课。

第二句是关键：BibiGPT 自己承认**纯靠画面变化检测，在画面不变的视频上会失效**。

### 3.2 Slide Mode 的四步（博客描述）

```text
1. 场景变化检测：分析相邻帧的视觉差异，只在显著变化时捕获
2. 去重与筛选：去掉重复或近似帧
3. 字幕匹配：每张帧关联对应时段的字幕文本
4. 智能参数调优：根据视频时长和类型，自动选择采样间隔和检测阈值
```

第 4 点值得单独记：**参数不是固定的**。官方说明是"短视频用更细的采样间隔，长视频用更宽的阈值，避免产生过多冗余帧"。也就是采样密度随视频时长自适应，这是一条可以直接抄的工程规则。

### 3.3 帧数超过模型上限时怎么挑（文档明确）

这是 BibiGPT 最值得抄的一条规则。用视觉模型逐帧读图时，帧数受模型上限约束，超了就要丢弃一部分。官方写明：

> 当静止帧超过模型上限时，帧是从**镜头变化（shot changes）和字幕里的话题切换（topic shifts）**挑出来的，**不是等间隔挑的**。界面上叫 "Auto-select by scene"。
> 没有字幕时，用**视觉变化 + 时间轴覆盖度**。
> 长的 talking-head（纯讲话人头）片段保留更少的帧。

拆开看是三个信号：

- 有字幕：镜头变化 + 字幕话题切换，两个信号共同决定挑哪些帧
- 无字幕：视觉变化 + 时间轴覆盖度（保证整条时间轴上都有帧，不会某一段完全空着）
- 画面不变的长片段：主动少留帧

"时间轴覆盖度"这条正好补上了场景检测在长静止画面上只出 1 帧的问题——不是靠固定间隔补帧，而是把"整条时间轴被均匀覆盖"当成挑选目标。

### 3.4 场景转写（scene transcript）

官方定义：在画面或话题发生变化的地方把视频切开，每个块写这段时间内说了什么，带起止时间。跟普通字幕文件的区别是每个块同时绑定了画面段，可以搜一句话直接跳到对应的那张 slide。

## 四、腾讯会议：多流录制，共享屏幕本来就是独立一路

### 4.1 取帧的前提条件（官方明确）

腾讯会议官方新闻《千万不要这样用云录制》原文：

> 一场会，录出好几条：**共享屏幕是一条视频；正在说话的人，也是一条视频**。回看的时候，想盯 PPT 看，就看 PPT；想看谁在讲，就看谁在讲。
> 录制前在设置-录制-录制模式中，打开**多流录制**，分别录制会中多个画面，不用在一整段视频里来回拖。

这一条决定了它整个取帧逻辑的形状：**不需要在合成画面里找 PPT 区域、不需要透视裁剪、不需要过滤人像干扰**。共享屏幕本来就是单独一个视频文件，要哪张图就直接从这条流上取帧。

这是四家里代价最低的一条路，但它的前提是"录制时能拿到独立的多路流"。

### 4.2 取完之后怎么用（实测可确认，官方未写规则）

腾讯会议官方帮助页《智能录制》列出的能力是：智能总结、纪要、待办、章节、发言人、话题。**没有写画面抓取**——这个能力 2026 年 9 月才上线，帮助文档还没补进去。

腾讯新闻《一手实测｜「图文并茂」的腾讯会议》（2026-09-11）记录的实际行为：

- 图文纪要智能抓取会议中的共享画面，**裁剪成图片插入总结**
- 实测案例：会中共享的是一份 Word 研究报告，纪要里就自动截取了共享屏幕里的那页 Word，截图直接嵌在对应的讨论段落里
- 所有纪要文字带时间戳，点击右上角的会议视频自动跳到对应时刻；问元宝的回答也带可跳转的时间戳
- 支持按时间线加个人笔记，笔记和纪要正文分开存放

"裁剪"这两个字说明取帧之后还有一步处理（去掉共享画面周围的黑边和播放器界面元素），具体裁剪规则官方没有说明。

官方**没有说明**的是：什么时刻取帧、取多少张、是不是检测画面变化。这些只能从行为上推断——图片是嵌在"对应的讨论段落"里的，也就是按纪要段落所在的时间位置，去共享流上取那一刻的画面。这个推断没有官方佐证。

### 4.3 画面帧反过来喂给 ASR（官方明确）

腾讯会议 ASR 能力升级的官方通稿（2026-09）里写：

> 会议里最容易听错的是人名、产品名、项目代号这类专有名词……其中**投屏的图片、ppt、视频等视觉信息常为多模态，它们是对 ASR 上下文理解的有力补充**，而传统 ASR 并不能理解情景、领域以及当前屏幕共享的信息，导致其识别效果提升空间很有限。

也就是共享画面上的文字被拿来当 ASR 的上下文，纠正专有名词识别。这是四家里唯一明确把画面帧反向用于提升转写质量的。对 AIVideo 有直接价值：抽帧 OCR 的结果不要只当配图，要当作 ASR 的热词来源做一次纠正。

### 4.4 待核实的部分

有第三方代理公司的文章写"当检测到 PPT 翻页、白板书写等动作时，系统会自动生成章节标记"。腾讯官方没有这个说法，不能当结论用。

### 4.5 对我们的意义

"多流录制"这条路 AIVideo 走不了——用户上传的是一个已经合成好的视频文件，系统只能看到像素，拿不到独立的共享流。

能抄的是两点：

1. **画面上的文字反过来纠正 ASR 术语**（官方明确这样做）。
2. **图片嵌进对应的纪要段落，而不是单独成册**。纪要按时间顺序走，图跟着段落走。

## 五、飞书妙记：没有公开的抽帧能力

### 5.1 官方能确认的部分

飞书帮助中心《使用录制功能》写明：

> 云录制：会中音频、**参会人视频画面**和**共享内容画面**将被录制下来，会后自动生成录制文件（妙记）。
> 录制内容包括会中音频、参会人视频画面和共享内容画面。

飞书妙记产品页写明：

> 准确识别说话人，**会中共享的文档、发送的评论也会在妙记中同步呈现**。

妙记的界面是左边视频画面、右边文字记录，点文字跳到对应音视频位置。

注意和腾讯会议的区别：飞书这里说的是**共享的文档**（结构化对象，比如一个飞书文档）同步呈现，不是"从共享画面流里抽帧"。

### 5.2 官方没有的部分

翻遍飞书帮助中心和妙记产品页，**没有任何一处说明"从录制视频中抽取关键画面帧"**。妙记宣传的 AI 能力集中在转写、发言人识别、章节分割、智能纪要、待办提取、翻译上。

第三方实测文章提到飞书妙记"自动插入了关键画面截图作为段落配图"，这个说法**没有官方文档佐证**。合理的推测是：它呈现的是会中共享内容（共享文档本身是结构化对象，屏幕共享画面也是独立的录制流），不是对合成后的录像做视觉分析。但这是推测，不能当结论用。

### 5.3 对我们的意义

飞书走的是"**在系统侧直接拿共享内容**"这条路，前提是内容本来就在飞书会议里。这条路对 AIVideo 不成立。

真正能抄的是通义听悟（对视频文件做静止窗口检测）、BibiGPT（画面变化 + 自适应参数 + 覆盖度挑选）、腾讯会议（画面文字反哺 ASR）。

## 七、可以抄进 AIVideo 的五条

1. **用"静止窗口"判定 PPT 页，不要用"画面变化"判定。** 通义的做法是检测画面变完之后是否进入持续静止，静止窗口才是这一页的边界。这比"检测到差异就取帧"更抗干扰，也顺带解决了过渡动画的问题。

2. **先密集采样，再事后判断。** 固定间隔先把帧采下来，判定和校准放在后面做。不要在"检测到变化的那一瞬间"才去解码取帧，那时候画面可能正在过渡。

3. **采样密度随视频时长自适应。** 短视频细、长视频粗（BibiGPT 明确写了这条）。再叠一个帧数硬上限。

4. **帧数超限时按语义挑，不要等间隔砍。** 有字幕就按话题切换点挑，没有字幕就按视觉变化 + 时间轴覆盖度挑，保证整条时间轴上不会出现大段没有图。长的纯讲话片段主动少给帧。

5. **帧上的 OCR 结果反过来喂 ASR。** 腾讯会议官方明确把投屏画面上的文字当作 ASR 的上下文来纠正人名、产品名、项目代号。AIVideo 抽帧 OCR 的结果不要只当配图用，要拿去做一次术语纠正。

**不能抄的三条**：

- 腾讯会议的"多流录制"——前提是录制时能拿到独立流，上传视频的场景没有这个条件。
- 飞书的"共享文档同步"——前提是内容本来就在飞书系统里。
- 通义要求"PPT 是画面主体、人不能在前面走动"。网课录屏里讲师画中画是常态，AIVideo 需要在抽帧前先把人像区域排除掉，或者只检测画面中面积最大的稳定区域，否则通义那一套静止窗口检测会被画中画的人像动作持续打断。

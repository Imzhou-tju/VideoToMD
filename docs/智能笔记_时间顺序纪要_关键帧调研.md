# 智能笔记：时间顺序纪要 + 关键视频帧 调研

调研时间：2026-10-06
调研对象：网课 / 讲座 / 录屏类视频的「视频 → 图文笔记」产品，以及关键帧提取的工程做法

---

## 一、结论

现有产品没有一家是把视频逐帧喂给大模型的。所有产品的链路都是同一条：

> 找画面变化 → 候选帧去重 → 挑出稳定清晰的代表帧 → 把帧绑到它对应的时间段和那段时间的转写文本 → 按时间顺序生成「文字 + 图片」交错的笔记

差别只出现在三处：

1. **帧从哪来**：浏览器扩展直接取播放器里的画面（无光标、无播放条），还是服务端用 FFmpeg 从视频文件抽帧，还是从会议系统里单独取「共享屏幕」那一路流。
2. **什么帧算关键**：只认「整屏大变化」（PPT 翻页），还是同时认「局部区域变化」（代码编辑、终端输出）。
3. **图片怎么进笔记**：嵌进 Markdown（Obsidian 生态），还是渲染成网页卡片（会议产品），还是导出 PDF/PPTX。

另外一个判断：只做字幕总结不做画面的产品（NoteGPT、Kimi、Mindgrasp）在网课场景里明显不够用，因为代码、公式、图都在画面上，音频里没有。这一点是多家产品自己在宣传页上反复强调的卖点。

## 二、产品对照

|---|---|---|---|---|
| HoverNotes | Chrome 扩展，从视频播放器直接取当前画面帧；一键截图按钮 | 手动一键 + AI 自动 | Markdown，存本地 Obsidian vault | 支持 YouTube / Udemy / Coursera / B站 + 本地文件；明确宣传「抓到的帧没有光标、没有播放器控件」 |

| Vid2notes | ASR 转写 + 抽关键帧当截图织进笔记 | Markdown / CSV / TXT / SRT，带章节和说话人 |

| NoteGPT / Mindgrasp / Turbo AI / StudyFetch | 基本只走字幕，不带画面 | 纯文字笔记 |

### 2.3 会议产品路线

| 产品 | 画面处理 |
|---|---|
| 腾讯会议「图文纪要」 | 前提是多流录制——共享屏幕本来就是独立一路流，不需要在合成画面里找 PPT 区域；抓取后裁剪成图片插进对应讨论段落；每条文字带时间戳可跳播；画面上的文字还被官方明确用作 ASR 上下文来纠正专有名词；支持 6 套模板 |

这一条对网课场景最直接的启发：**共享屏幕流和摄像头人像流要分开处理**。网课视频里同样存在两类画面——投屏/PPT/代码编辑器和教师人像，混在一起抽帧会抽出大量人像帧。

## 三、关键帧链路：每一步具体怎么做

### 步骤 1：产生候选帧

三种采样策略，实际产品都用「场景检测 + 兜底」的组合：

```python
# 均匀采样：每 N 秒一帧。简单，但一张 PPT 停 5 分钟会浪费大量重复帧
ffmpeg -i input.mp4 -vf fps=1/5 frame_%05d.jpg

# 场景检测：只在画面发生明显变化时取帧（PySceneDetect）
from scenedetect import detect, ContentDetector
scene_list = detect(video_path, ContentDetector(threshold=27.0))
# 返回 [(start, end), ...]，每个场景取一帧，一般取场景中部而不是第一帧
```

只做场景检测有个已知缺陷（claude-watch 的 README 里明确写了）：**一张 PPT 停 5 分钟，场景检测只产出 1 帧，整段时间在笔记里就是空白**。它的做法是加「覆盖率下限」：

```text
场景检测出帧 + 长时间静止段每 45 秒强制补一帧
→ 一张 slide 停留 5 分钟也能拿到约 7 帧而不是 1 帧
```

所以正确的候选帧策略是：场景检测为主 + 长段按固定间隔补帧 + 帧数上限（claude-watch 默认硬上限 80 帧，因为帧数直接线性放大 token 成本）。

### 步骤 2：去重

场景检测之后仍然会有大量近似帧（鼠标移动、光标闪烁、讲师走动）：

```python
# 感知哈希：快速去掉「只有光标动了」的帧
from PIL import Image
import imagehash
h1 = imagehash.phash(Image.open("f1.jpg"))
h2 = imagehash.phash(Image.open("f2.jpg"))
if (h1 - h2) < 5:      # 汉明距离小于阈值判为同一张
    drop()

# CLIP 语义去重：去掉「像素不同但语义相同」的帧，且能直接和文字检索打通
emb = clip_model.get_image_features(processor(images=frames, return_tensors="pt"))
# 相邻帧余弦相似度 > 0.95 判为重复
```

工程顺序固定是：先场景检测粗筛 → 再哈希去重 → 最后才跑 CLIP。不要对每秒帧都跑 CLIP，长视频跑不动。

### 步骤 3：挑「稳定帧」而不是「变化帧」

这一步决定了截图能不能看，是很多粗糙实现翻车的地方：

- 场景切换的那一瞬间常常是过渡动画的中间态（PPT 淡入到一半、编辑器滚动到一半），取到的是糊的、半张的。
- 代码类内容尤其明显：讲师正在打字，帧里是打了一半的代码行。

做法：在场景变化之后，**等画面稳定下来再取帧**。判定方式是连续若干帧之间差异低于阈值，取稳定窗口的最后一帧（或中间帧）。同理，可以用拉普拉斯方差做清晰度过滤，把运动模糊的帧丢掉：

```python
import cv2
score = cv2.Laplacian(cv2.cvtColor(frame, cv2.COLOR_BGR2GRAY), cv2.CV_64F).var()
if score < 100:   # 模糊，丢弃
    drop()
```

### 步骤 4：给帧分类

网课里的关键帧不是一类，处理方式不同。学术项目 lecture2notes 的做法是训练一个 9 类分类器（slide / presenter_slide / 其他），slide 和 presenter_slide 走不同处理：拍屏带讲师的帧要做**透视裁剪**把 PPT 区域抠正。

工程上不训练模型也能分，用规则粗分：

| 帧类型 | 判据 | 处理 |
|---|---|---|
| PPT / Keynote 页 | 整屏变化大 + 停留时间 > 15 秒 + 中间大片纯色背景 | 保留，OCR 标题和要点 |
| 代码编辑器 | 大面积深色背景 + 等宽字体区域 + 行号 | 保留，交给视觉模型直接读成代码块 |
| 终端输出 | 深色背景 + 出现提示符样式文本 | 保留，抓新输出出现的那一帧 |
| 白板 / 手写 | 浅色背景 + 笔迹 | 保留 |
| 教师人像 | 人脸占屏 + 背景不变 | 丢弃或只留章节开头一张 |

### 步骤 5：帧里的内容怎么提取出来

两条路，各有适用面：

- **OCR**：中文用 PaddleOCR，英文用 Tesseract / EasyOCR。适合 PPT 标题、正文要点这种规整排版。**对代码帧效果很差**——缩进丢失、符号错乱。
- **视觉模型直接读图**：把帧原图丢给多模态模型，让它输出「这帧在讲什么」+「画面上的代码原文」。适合代码、公式、图表。claude-watch 就是这么做的：每一屏代码帧由模型转写成可运行的 fenced code block。

实践里是组合用：PPT 帧走 OCR（便宜、可全文检索），代码和公式帧走视觉模型（贵但准）。给帧配文字时，把该帧时间点前后 ±30 秒的转写文本一起塞给模型，让它结合上下文描述这一帧：

```python
prompt = f"结合这段课堂转写描述这张画面在讲什么：{transcript_around_timestamp}"
```

### 步骤 6：帧和时间段对齐

这一步是「时间顺序纪要」能不能成立的关键。做法是把视频时间轴切成**视觉段**（画面内容基本不变的一段连续时间），每段挂：起止时间、代表帧文件、该帧 OCR/视觉模型描述、该时间窗内的 ASR 文本。

```text
[00:12:30 - 00:15:40]  视觉段 #17
  代表帧: frame_017.jpg（稳定帧，取自 00:12:38）
  帧类型: PPT
  画面文字: 「二叉树的三种遍历」
  该段转写: 接下来讲前序、中序和后序，区别在根节点什么时候被访问……
```

BibiGPT 把这一步叫「场景转写（scene transcript）」，每个场景一个文本块带起止时间，点一下跳到对应时刻。OCR 文本和 ASR 文本还能互相校验：两段文本术语重合度高，说明画面和讲解对得上。

### 步骤 7：生成纪要产物

最终产物是一条按时间排序的条目列表，每条包含时间戳、小标题、正文、图片、证据来源：

```json
{
  "sections": [
    {
      "startMs": 750000,
      "endMs": 970000,
      "title": "前序遍历的定义与递归实现",
      "body": "根节点 → 左子树 → 右子树，递归终止条件是节点为空……",
      "frameId": "frame_017.jpg",
      "frameCaption": "幻灯片：二叉树遍历的三种顺序，附递归代码片段",
      "evidence": [
        { "source": "ASR", "content": "先访问根节点，再递归左子树" },
        { "source": "OCR", "content": "前序遍历：根、左、右" }
      ]
    }
  ]
}
```

渲染方式按载体分：Markdown 用 `![](frame_017.jpg)` 图文混排（Obsidian / Typora 直接可读）；网页用卡片流，图片和时间戳可点击跳播（腾讯会议、飞书妙记的做法）。

## 四、四个已知的坑

1. **长静止画面帧太少**。一张 PPT 停 5 分钟，纯场景检测只出 1 帧。必须加固定间隔补帧。
2. **过渡帧和半截代码**。取变化瞬间而不是稳定后的帧，截图糊、代码断行。
3. **代码 OCR 质量差**。代码帧不要走 OCR，直接让视觉模型读图输出代码块。
4. **摄像头拍屏**。教室录像里 PPT 是斜的、带讲师人像，需要先做透视裁剪再 OCR，否则文字识别率掉一大截。

另外还有一个成本约束：帧数和 token 成本线性相关，1 小时网课场景检测后通常 40–80 帧，产品普遍设硬上限（80 帧左右），再用模型对每帧打重要性分挑 20–30 张进最终笔记。

## 五、对 AIVideo 项目的落点

### 5.1 现在已经有什么

按 `README.md` 和 `AIVideo_ARCHITECTURE.md`：FFmpeg 抽音频 + 场景变化检测抽关键帧，ASR 和关键帧 OCR 并行，按时间窗口合并成 `VideoSegment`（时间窗 + ASR 文本 + OCR 文本 + 帧文件），再按 5 分钟构建语义块，Agent 走 Planner-Executor-Critic 输出 `conclusions / evidence / suggestions`。

也就是说：**多模态时间轴底座已经有了**，缺的是「纪要」这个产物形状和几处帧质量处理。

### 5.2 缺什么

| 缺口 | 现在的表现 | 要补的 |
|---|---|---|
| 没有「视觉段」概念 | 按固定时间窗切，一帧可能被切进两个窗，或者一个窗跨两次翻页 | 改成按画面变化切视觉段，段内挂一帧代表帧 |
| 代表帧可能落在过渡帧 | 场景检测出变化就取帧 | 取稳定窗口内的帧，并用清晰度过滤 |
| 没有帧去重 | 鼠标移动、光标闪烁会产生近似帧 | 加感知哈希去重，长视频再叠 CLIP 语义去重 |
| 没有帧分类 | 所有帧一视同仁走 OCR | 按 PPT / 代码 / 终端 / 人像分流，代码帧走视觉模型而非 OCR |
| 没有时间顺序纪要产物 | 输出是扁平的 conclusions + evidence 数组 | 新增 `notes.sections[]`，每节带起止时间、标题、正文、帧文件、帧描述、证据 |
| 长静止段无帧 | 一张 PPT 停很久，整段没有图片 | 补固定间隔兜底帧 + 帧数上限 |

### 5.3 建议的落地顺序

1. 先在 `VideoContext` 里增加视觉段结构（画面变化切段 + 每段一帧 + 稳定帧选取），这一层不改 Agent。
2. 加帧去重和帧分类，代码帧改走视觉模型读图。
3. 新增「生成时间顺序纪要」的分析目标，产物是 `sections[]` 而不是现有的三段式 JSON。
4. 前端按时间顺序列出条目，图片和时间戳可点击跳播。

前三步都在已经有 Checkpoint 的异步链路里，单个视频解析一次，后面追问可以复用，不用重跑 ASR 和抽帧。
